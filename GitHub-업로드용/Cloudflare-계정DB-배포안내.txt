길 — 계정별 여행 계획 저장 / Cloudflare 업로드 안내

GitHub PR 검토·main 반영 → 같은 main 버전의 Cloudflare ZIP 생성 → 배포 순서로 진행합니다.
기존 ZIP에 최신 수정이 들어 있다고 가정하지 말고 생성한 버전과 파일을 확인하세요.

이번에 처음 한 번만 설정할 것

1. Cloudflare 대시보드 → Storage & Databases → D1 SQL Database → Create Database
   DB 이름: gil-plans
   이 DB는 로컬 DB와 별개입니다. 로컬에서 만든 테스트 계정·계획은 올라가지 않습니다.

2. 만든 gil-plans → Console
   현재 저장소의 account-schema.sql을 메모장으로 열어 전체 내용을 복사합니다.
   Console에 붙여넣고 Execute를 누릅니다. SQL 파일을 사이트 ZIP 업로드 칸에 넣지 않습니다.
   기존 테이블을 지우는 명령은 없으며, 계정·세션·계획·소셜 식별·공유 테이블과 인덱스를 추가합니다.

3. Workers & Pages → rode-hackathon → Settings → Bindings → Add
   유형: D1 database
   Variable name: DB (대문자 두 글자)
   Database: gil-plans
   Production 환경에 연결하고 저장합니다. Preview도 사용할 경우 별도로 연결합니다.

4. 같은 프로젝트 → Variables and Secrets → Add
   유형: Secret / Encrypt
   이름: AUTH_SECRET
   값: 여행의-결\.local\AUTH_SECRET.txt 파일의 내용 한 줄
   이름과 값만 입력하며 = 기호나 따옴표는 넣지 않습니다.
   이 비밀값은 소셜 계정 식별자와 로그인 상태 보호에 사용됩니다. 함부로 바꾸지 마세요.
   변경·분실하면 기존 소셜 계정 식별이 유지되지 않아 기존 계획에 접근하지 못할 수 있습니다.
   비밀 파일과 DB 파일은 사이트 업로드·제출·공유 대상이 아닙니다.

   기존 DATA_GO_KR_SERVICE_KEY, KAKAO_REST_API_KEY 설정은 유지합니다.
   두 API 키도 가능한 Secret 유형으로 보관합니다.

5. social-login-setup.md에 따라 소셜 제공자의 앱·콜백 URL과 아래 환경변수를 등록합니다.
   SOCIAL_AUTH_BASE_URL=https://rode-hackathon.pages.dev
   GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET
   KAKAO_LOGIN_CLIENT_ID / KAKAO_LOGIN_CLIENT_SECRET
   네이버는 공개 서비스 검수 완료 후 NAVER_CLIENT_ID / NAVER_CLIENT_SECRET을 등록합니다.
   준비가 끝나지 않은 제공자의 키는 운영 환경에 등록하지 않습니다.
   소셜 제공자가 없으면 로그인할 수 없지만 이 기기에서 계속 노트를 편집할 수 있습니다.

6. GitHub main 반영본으로 새로 생성한 Cloudflare ZIP 업로드 → 저장 및 배포
   프로젝트 전체 폴더, .env, .local, SQL 파일을 업로드하지 않습니다.
   Secret과 DB 연결은 설정을 저장한 뒤 만든 새 배포부터 적용됩니다.
   ZIP은 이미 빌드돼 있어 별도 빌드 명령이나 Node 호환 옵션은 필요하지 않습니다.

‘계정 저장 준비 중’이 계속 보이면 Production의 DB 바인딩과 AUTH_SECRET을 확인하세요.
설정을 저장한 뒤 새 배포를 만들고 사이트의 ‘다시 확인’을 누릅니다.
ZIP 업로드만으로 DB나 Secret이 만들어지지는 않습니다.

배포 후 확인

- ‘소셜 로그인’에서 설정된 Google·카카오·네이버 제공자로 로그인합니다.
- 별도 회원가입·아이디·비밀번호 입력 없이 첫 소셜 로그인에서 여행 계정을 만듭니다.
- 여행 노트를 만든 뒤 ‘계획표 저장’에서 이름을 붙여 저장합니다.
- 다른 브라우저나 휴대폰에서 같은 계정으로 로그인 → ‘저장한 계획’ → 불러오기를 확인합니다.
- 다른 계정으로 로그인하면 이전 계정의 목록·작성 중인 노트가 보이지 않아야 합니다.
- 관광지·식당 목록과 교통편 조회도 함께 확인합니다.

여행 노트는 자동으로 계정 DB에 업로드하지 않습니다. 편집 중에는 계정별 브라우저 임시 저장을 사용하고,
‘변경사항 저장’을 누르면 계정 DB를 갱신합니다. 다른 기기와 수정이 겹치면 덮어쓰기 대신 선택을 안내합니다.
계정당 최대100개, 계획당 최대256KiB입니다. 계정 복구는 소셜 제공자의 절차를 이용합니다.
기존 아이디·비밀번호 가입·로그인은 종료하며 해당 방식의 세션으로 계정 노트에 접근할 수 없습니다.
기존 사용자·계획 데이터는 삭제하지 않지만 새 소셜 계정으로 자동 이전하거나 연결하지 않습니다.
관광정보가 API에서 삭제된 경우 복원이 실패할 수 있으며, 이때 저장한 계획은 삭제하지 않습니다.

로컬 실행과 재빌드

Node.js 24 이상. GitHub-업로드용 폴더에서 npm start를 실행하면 로컬 SQLite DB와 비밀값을 자동 준비합니다.
로컬 DB: GitHub-업로드용\.local\gil.sqlite
로컬 서버와 실제 Cloudflare D1은 서로 독립적입니다.
수정 후 ZIP을 다시 만들 때: npm ci → npm run build:cloudflare

개발용 인증 구성

인증은 소셜 제공자의 서버 인증 코드 방식만 사용하며 제공자의 접근·갱신 토큰은 저장하지 않습니다.
검증된 제공자별 식별자를 AUTH_SECRET으로 HMAC 처리해 계정을 구분합니다.
기존 비밀번호 컬럼은 데이터 보존과 기존 스키마 호환을 위해 남지만 비밀번호 인증에 사용하지 않습니다.
세션은 HttpOnly/SameSite 쿠키(HTTPS에서는 Secure)로, DB에는 세션 토큰의 해시만 보관합니다.
